> **공식**: Codex(CLI, GPT-5.6 Sol)로 cli-pipeline+skills 방식으로 26개 테스트기법 지시와
> 유명 테스트 스킬 4종을 조건당 80회(IMAP은 40회)씩 실행해 Zstd·IMAP 구현 정답률·비용을
> 실측 비교 → **부정 결과**: 이름난 테스트 기법·스킬 대부분이 기대만큼 작동하지 않았고,
> 무지시 기본값이 평균 이상이었다

## 무엇을 자동화했나

Dan Luu가 "코딩 에이전트가 효과적인 테스트 기법을 쓰게 하면 품질 기준을 맞추기는
쉬워졌지만, 소프트웨어 품질 자체는 오히려 나빠지고 있는 것 같다"는 이전 관찰에서 출발해,
"테스트에 대한 전문성이 없는 사람이 어디선가 '이 기법/라이브러리를 써야 한다더라'는
말을 듣고 에이전트에게 그대로 지시했을 때 실제로 정확성이 개선되는가"를 실측으로
검증하는 평가 파이프라인을 만들었다. 같은 Zstd 구현 프롬프트에 "Use test-driven
development", "Use Lean 4", "Use property-based testing" 같은 addendum 26가지와 공개
테스트 스킬 4종을 각각 붙여 반복 실행하고, 숨겨둔 테스트 통과율 대비 비용(토큰)을 비교했다.
IMAP RFC 구현으로 재검증했고, 몇몇 다른 RFC에서도 소수 런을 시도했다.

## 어떻게 구성했나 (아키텍처)

- **대상 구현**: Zstd(압축 포맷, 비트 조작 중심)와 IMAP RFC(프로토콜, 비즈니스 로직
  중심). 모든 구현은 Rust.
- **26개 프롬프트 조건**: ACL2, Alloy, "Audit and fuzz risky areas", "Audit first",
  Creusot, Default(무지시), Differential testing, Fuzzing, Hegel, Insta, Judgement(에이전트
  스스로 최선의 기법을 고르게 함), Kani, Lean 4, "Make no mistakes"(농담성 조건),
  Metamorphic testing, Mutation testing, Property-based testing, Proptest, QuickCheck,
  rstest, Rust 기본 테스트 프레임워크, SMT 솔버(Z3·cvc5·Yices 모두 사용 가능),
  Spin, TDD, TLA+, Verus.
- **4개 스킬**: Hegel 공식 스킬(Hegel은 Hypothesis 기반 프로퍼티 기반 테스트 라이브러리),
  ECC Rust 테스트 스킬(GitHub 25만 스타·3.8만 포크 스킬 모음), Trail of Bits 프로퍼티
  테스트 스킬, 그리고 저자가 직접 2분 정도 들여 쓴 커스텀 스킬. 저자 본인 것을 제외하고
  나머지 셋은 "Codex에게 관련 스킬을 찾아보라고 했을 때 상위에 뜬 것들"을 그대로 썼다.
- **실행 규모**: Zstd는 조건×노력수준(medium/xhigh)당 80회, IMAP은 조건당 40회, 다른
  RFC는 개별적으로 소수 회. 숨겨둔 테스트 통과율(정확도)과 토큰 비용을 함께 기록했다.
  실험 전 저자가 각 조건의 결과를 예측(prediction)해 사전 등록했다.

## 벤치마크 데이터

| 항목 | 내용 |
|---|---|
| 모델 | Codex CLI, GPT-5.6 Sol, medium·xhigh 두 노력 수준 |
| 비용 | Hegel 스킬 +26%(medium)/+41%(xhigh, 정확도 개선 없음); Rust 기본 테스트 명시 지시 시 테스트 2배(medium)/+25%(xhigh, 정확도 무관); Audit은 xhigh에서 비용 대폭 증가; 그 외 조건별 세부 비용은 본문에 수치로 제시되지 않고 그래프로만 공개(미확인) |
| 권한 | 미확인 — 사람 개입 없는 단일 턴 자율 실행. ToB 스킬의 "의존성 추가 승인 필요" 안내는 이 환경에서 실행되지 못함 |
| 성숙도 | prototype — 저자 개인 리서치 블로그의 벤치마크 실험, 상용/프로덕션 배포 사례 아님 |
| 근거 수준 | measured — 조건당 80회(Zstd)·40회(IMAP) 반복 실측, 사전 등록된 예측과 결과 대조 |

## 성과와 수치 (부정 결과를 그대로 기록)

**26개 조건 — 뚜렷한 승자 없음**

| 결과대 | 조건(순서 없음, 저자가 순위화를 거부함) |
|---|---|
| 상대적으로 나은 편 | Proptest, Property-based testing(일반), 저자 커스텀 스킬, TLA+, Metamorphic testing, Fuzzing |
| 중간 | Default(무지시), Audit, Mutation testing, SMT 솔버 |
| 상대적으로 나쁜 편 | TDD, QuickCheck, Lean 4, Alloy, Verus, Differential testing, Hegel |

- **Default(무지시)가 평균 이상**: "특정 기법을 쓰라고 지시하는 것"이 대체로 에이전트를
  쓸모없는 작업으로 이끌기 때문에, 아무것도 지시하지 않는 편이 나은 경우가 많았다.
- **"Make no mistakes"(농담 조건)가 대부분의 조건보다 좋았다**: 아무 일도 안 하는 것이
  실제로 해로운 일을 하는 것보다 낫다는 저자의 예측(95% 확신)이 그대로 맞았다.
- **형식검증 도구(Verus·Alloy·TLA+ 등)는 대부분 실패**: 에이전트는 실제 코드를 검증하는
  대신 `A => A` 같은 공허한 명제나 버그와 무관한 지엽적 속성만 증명했다. Verus 사용
  조건에서도 정확성은 결국 표준 Rust `#[test]` 유닛 테스트에 거의 전적으로 의존했다.
- **차등 테스트(Differential testing)도 실패**: 160회 중 135회가 "차등 테스트 비슷한 것"을
  했지만, 독립적인 두 구현을 만들어 비교하는 대신 같은 코드를 두 번 써서 같은 버그를
  양쪽에 그대로 남겼다.
- **Rust 기본 테스트 명시 지시**: 테스트 개수는 늘었지만(medium 2배, xhigh 25%↑) 정확도는
  달라지지 않았다 — 테스트가 위험 영역을 더 많이 커버하지도, 잘못된 동작을 인코딩한
  테스트 비율을 줄이지도 못했다.
- **Audit**: 152/160이 실제로 감사를 수행했고 151이 문제를 찾아 수정했다고 답했으나,
  대부분 신선한 컨텍스트로 독립 감사를 하지 않고 이미 저지른 실수를 감사에서도 반복했다.
  42회는 별도 에이전트로 감사했으나 오히려 결과가 더 나빴다. xhigh에서는 최고 정확도를
  기록했지만 비용이 크게 늘었고, medium에서는 평균 이하였다.

**4개 스킬 — 3개가 기대 이하, 1개는 최고점이지만 의도대로 작동 안 함**

| 스킬 | 결과 |
|---|---|
| Hegel 공식 스킬 | 정확도 개선 없음(오히려 약간 하락, 다만 무작위 범위 내). 비용만 26%(medium)·41%(xhigh) 증가. Hegel 저자 그룹 지인도 벤치마크로 결함을 확인했다고 저자가 후기에 덧붙임 |
| ECC 테스트 스킬(25만 스타) | 표면적 점수는 Default와 비슷해 보이지만, 스킬을 실제로 읽고 영향받은 에이전트만 골라보면 평균 이하(Rust 기본 프레임워크와 Creusot 사이). "스킬을 안 읽거나 늦게 읽은 에이전트가 우연히 잘한 것"이 평균 점수를 끌어올린 착시였음 |
| Trail of Bits 프로퍼티 테스트 스킬 | 160회 중 108회만 스킬을 열람. proptest 사용을 권하지만 신규 의존성 추가에 승인이 필요하다는 안내가 단일 턴 자율 실행 환경에서 지켜지지 못해 프로퍼티 테스트가 초보적 수준에 그침 |
| 저자 커스텀 스킬(2분 작성) | 최고 점수를 받았으나 "설계대로 작동한 것은 아니다" — 핵심 지시였던 "고위험 영역 독립 재도출(신선한 컨텍스트, 기존 헬퍼 재사용 금지)"이 거의 실행되지 않았다 |

**저자의 최종 결론(원문 그대로 옮김)**: "규모와 상관없이, 대부분의 조건에서 에이전트는
기법/라이브러리의 이름만 알 뿐 거기서 가치를 뽑아내는 방법은 모른다. 이름을 지시해도
행동은 크게 바뀌지 않으며, 바뀌더라도 표면적으로만 그 기법을 흉내 낼 뿐 실제 가치를
만드는 활동은 거의 일어나지 않는다." 저자는 "직접 에이전트와 상호작용하며 반복적으로
피드백을 줄 때만" 효과적인 테스트가 가능했다고 덧붙인다 — 즉 이 실험이 보여준 것은
"이름만 던지는 지시"의 한계이지, 에이전트가 테스트를 절대 잘할 수 없다는 뜻은 아니다.

## 재현 가이드

- **난이도**: 상 (80회 이상의 반복 실행·숨겨진 테스트 셋 설계·비용 계측 파이프라인 구축
  필요, 통계적으로 유의미한 비교를 위해 상당한 실행 횟수가 필요함을 저자가 직접 강조)
- **준비물**: Codex CLI 등 반복 실행 가능한 코딩 에이전트, 숨겨진 검증 테스트 셋을 갖춘
  평가 대상 구현 과제, 조건별 프롬프트 addendum 목록, 비용·정확도 로깅 체계
- **핵심 단계**:
  1. 정답 여부를 객관적으로 판정할 숨겨진 테스트 셋이 있는 구현 과제를 정한다(저자는
     Zstd·IMAP RFC 사용)
  2. 비교하려는 테스트 기법·스킬 조건 목록을 정하고, 조건당 최소 수십 회(저자는 80회)
     반복 실행한다
  3. 정확도(숨겨진 테스트 통과율)와 비용(토큰)을 조건·노력 수준별로 함께 기록한다
  4. 결과 발표 전 예측을 사전 등록해 확증 편향을 줄인다
  5. 스킬을 평가할 때는 "스킬을 실제로 읽고 영향받은 런"과 "안 읽거나 무시한 런"을
     구분해서 봐야 한다 — 그렇지 않으면 ECC 사례처럼 착시가 생긴다

## 강의·AX 활용 포인트

- **강의**: "에이전트에게 방법론 이름만 던지면 안 된다"의 실증 근거로 유용하다. TDD·
  QuickCheck·형식검증 같은 유명 기법을 지시어로 던지는 것만으로는 코딩 에이전트 활용
  교육에서 기대하는 품질 향상이 나오지 않는다는 것을 실측 데이터로 보여준다. 특히 유명
  공개 스킬(25만 스타 저장소 포함)조차 기대 이하였다는 점은 "스킬/템플릿을 가져다 쓰면
  된다"는 안이한 기대를 교정하는 데 쓸 수 있다.
- **AX**: 조직이 코딩 에이전트에게 표준 테스트 방법론을 강제하려 할 때, "방법론 이름을
  프롬프트/스킬에 넣는 것"만으로는 품질이 담보되지 않는다는 경고 사례로 인용할 수 있다.
  도입 전 파일럿에서 실제 정확도·비용을 함께 측정하지 않으면 Hegel 스킬처럼 "비용만
  오르고 효과는 없는" 상황을 조직 전체 규모로 반복할 위험이 있다.
