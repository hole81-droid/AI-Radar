> **공식**: Claude Code를 페어 프로그래머로 활용해 C++ 기반 시맨틱 캐시(HotKV)를 구축 →
> 반복 질문의 Claude 호출을 가로채 → 호출·토큰·비용 70% 절감(응답속도 1.4~2.9초→127ms)

## 무엇을 자동화했나

1인 개발자(20년 경력)가 **LLM 응답용 시맨틱 캐시가 내장된 Redis 호환 인메모리 스토어
(HotKV, C++20)**를 직접 설계하고, Claude Code를 "명세는 내가 주고 구현은 맡기는" 페어
프로그래머로 활용해 구축했다. 목적은 "고객 지원처럼 비슷한 질문이 반복되는 트래픽에서
캐시가 Claude 호출을 얼마나 줄이고, 그 대가로 답변 품질을 얼마나 잃는가"를 **직접 계측**
하는 것.

## 어떻게 구성했나 (아키텍처)

- **엔진 설계(인간 담당)**: 스레딩 모델, 벡터 검색 경로의 락 경합(lock-contention) 등
  핵심 아키텍처 결정은 개발자 본인이 설계·검증.
- **Claude Code가 맡은 부분**: 벤치마크 자체(리플레이 하네스·조회 흐름·토큰 계산·LLM
  판정 파이프라인), Redis 8 대비 벡터 검색 락 경합 버그 수정, Claude Code가 HotKV의
  키·프롬프트·에이전트 메모리를 읽고 쓸 수 있게 하는 **MCP 서버**, LangGraph
  체크포인터·캐싱 게이트웨이, 12개 언어 SDK 패키징, 문서 사이트·웹사이트·클라우드
  콘솔 대부분.
- **캐시 매칭 로직**: 정규화된 질문의 해시로 **정확 일치**를 먼저 시도하고, 미스 시
  임베딩 코사인 유사도(임계값 0.81로 사전 고정) 기반 **시맨틱 일치**를 시도. 둘 다
  미스일 때만 실제 모델을 호출.
- **검증 방법**: 캐시 응답의 품질을 캐시 자신이 평가하지 않도록, **독립된 Claude
  모델이 모든 시맨틱 히트를 "신선한 답변"과 비교 채점**(자기 평가 배제).

## 벤치마크 데이터

| 항목 | 값 |
|---|---|
| 모델 | Claude Fable 5.1·Opus 5.5·Sonnet 5.5·Haiku 5.5 (4개 전부 동일 벤치마크) |
| 데이터셋 | Banking77(PolyAI, CC BY 4.0) 지원 질문 3,000건, 모델당 2회(캐시 미적용/적용) |
| 비용(3,000건당) | Sonnet 5.5: $5.51→$1.66 / Opus 5.5: $14.60→$4.50 / Fable 5.1: $30.31→$9.18 / Haiku 5.5: $0.27→$0.08 |
| 권한 설계 | 미확인 |
| 성숙도 | prototype (벤치마크 공개 단계, 상용 배포 사례 미확인) |

## 성과와 수치 (실측)

- **호출 횟수**: 모델당 3,000건 → 약 896~898건(약 70% 감소) — Anthropic 자체 프롬프트
  캐싱을 이미 켠 상태에 **추가로** 적용한 결과.
- **토큰**: 모델 평균 약 7.1~7.3M → 2.1~2.2M (약 70% 감소).
- **응답속도**: 중간값 1.4~2.9초 → 약 127ms(정확 일치 히트는 0.05ms).
- **구성**: 반복 트래픽의 39%가 완전 동일 질문, 31%가 바꿔 쓴 질문(paraphrase).
- **품질 트레이드오프**: 캐시 임계값 0.81에서는 캐시된 답변이 신선한 답변보다
  5.8~10.7점 낮게 평가됨. 임계값을 0.88 이상으로 올리면 그 격차가 노이즈 수준으로
  사라지지만 절감 효과도 70%→64%로 소폭 감소. "까다로운 유사 질문 쌍"(입금 vs 출금,
  카드 vs 계좌이체 등 119개) 테스트에서는 임계값 0.81일 때 62%가 여전히 캐시로
  잘못 응답돼, "임계값을 올려도 문제가 완전히 없어지지는 않는다"는 점도 함께 공개.
- 작성자 본인이 "독립된 측정 1회·판정 1회라 증거(proof)가 아니라 강한 힌트
  (strong hint)"라고 한계를 명시 — evidence를 measured로 기록하되 재현 샘플이 제한적임에
  유의.

## 재현 가이드

- **난이도**: 상 (벤치마크 설계 자체가 핵심 — 해시/임베딩 매칭 로직, LLM judge 파이프라인,
  품질 트레이드오프 계측까지 포함)
- **준비물**: 반복 패턴이 있는 실제/공개 지원 데이터셋(Banking77 등), 임베딩 모델,
  독립 LLM judge, Claude API 접근
- **핵심 단계**:
  1. 해시 기반 정확 일치 캐시를 먼저 구축(가장 저렴하고 안전한 절감)
  2. 임베딩 코사인 유사도 기반 시맨틱 매칭을 추가, 임계값을 보수적으로 고정
  3. 캐시 응답을 자기 평가가 아닌 **독립 모델**로 품질 검증
  4. 임계값을 바꿔가며 "절감 vs 품질" 트레이드오프를 직접 스윕
  5. 의도적으로 헷갈리는 질문 쌍으로 캐시의 오매칭률을 별도 테스트

## 강의·AX 활용 포인트

- **강의 소재**: "캐싱으로 LLM 비용을 줄인다"는 흔한 주장을 **정량 계측 방법론**으로
  보여주는 드문 사례 — 프롬프트 캐싱 위에 시맨틱 캐싱을 얹을 때 품질 손실을 어떻게
  측정해야 하는지까지 포함해 AI 비용 최적화 모듈에 바로 쓸 수 있다.
  "캐시 벤더가 공개하지 않는 부분"(품질 저하 가능성)을 스스로 검증한 태도 자체도
  비판적 AI 도입 사례로 가치 있다.
  Claude Code의 역할(아키텍처는 인간이 설계, 구현·테스트·패키징을 위임)은 "vibe coding"과
  "agentic engineering"의 경계를 보여주는 실례다.
- **AX 관점**: 고객 지원처럼 반복 질문이 많은 업무에 LLM을 투입할 때, 캐싱으로 비용을
  3~4배 줄일 수 있다는 구체적 수치 근거 — 다만 "캐시 품질 검증 체계 없이 캐싱만
  적용하면 안 된다"는 경고도 함께 와야 한다.
