> **공식**: Claude Code·Codex·Cursor로 격리 VM 기반 병렬 에이전트 오케스트레이션
> (cli-pipeline+subagents)을 활용해 개인 개발자의 소프트웨어 개발 업무 전체를 수행
> → 6개월간 "경력 중 최고 생산성", 피크 시 동시 20개 에이전트 운영 (주장)

## 무엇을 자동화했나

exe.dev 소속 개발자가 "더는 손으로 코드를 쓰지 않는다(No more code by hand)"는 개인
규칙을 세우고 6개월간 실제 업무 개발을 Claude Code·Codex·Cursor(모델은 GPT-5.3·
Opus 4.6 언급) 에이전트에 위임했다. 코드 작성뿐 아니라 테스트 실행·CI 트리거·앱 구동·
스크린샷 캡처까지 에이전트가 처리하고, 사람은 결과 검토와 아키텍처 의사결정만 담당하는
구조로 옮겨갔다.

## 어떻게 구성했나 (아키텍처)

1. **병렬 실행**: 여러 에이전트를 exe.dev VM 각각에서 동시에 구동.
2. **오케스트레이션**: 자체 개발 도구 `botd`가 VM 프로비저닝, 에이전트 진행상황 추적,
   대화 히스토리 보존을 담당.
3. **격리 전략**: 에이전트마다 독립 VM(bash 접근권)을 배정해 파일 충돌·자원 경합을
   원천 차단 — 승인 게이트 없이도 안전하게 자율 실행할 수 있는 기반.
4. **보안 경계**: 외부 서비스 연동은 가능한 읽기전용으로 제한하고, 자격증명은 VM 내부에
   저장하지 않고 프록시를 경유해 처리.
5. **검증 루프**: 에이전트가 테스트·CI·앱 구동·스크린샷까지 자체 수행해, 사람의 개입은
   결과 검토 단계로 좁혀짐.

핵심 주장은 "모델이 곧 루프의 역량을 결정한다"는 것 — 개발자급 도구(셸·컴파일러·브라우저
접근)를 격리 환경 안에서 쥐어주면 매 행동 승인 없이도 안전하게 자율 실행할 수 있고,
병목이 "실행 속도"에서 "아키텍처 의사결정"으로 옮겨간다.

## 벤치마크 데이터

| 항목 | 값 |
|---|---|
| 모델 | Claude Code·Codex·Cursor 병행, GPT-5.3·Opus 4.6 언급(작업별 배분 기준 미확인) |
| 비용 | 미확인 |
| 권한 설계 | 에이전트별 격리 VM(셸 접근), 외부연동 읽기전용 우선, 자격증명 프록시 경유(VM 내 미저장) |
| 성숙도 | production(개인 실제 업무 6개월 운영, 오케스트레이션 도구 `botd`는 이후 폐기) |
| evidence | claimed (자기 보고 블로그, 제3자 검증 없음) |

## 성과와 수치

- "경력을 통틀어 가장 많이 출시한 6개월"이라는 주관적 평가(정량 비교 수치는 제시되지
  않음).
- 피크 시점 동시 실행 VM **약 20개**.
- 자체 오케스트레이션 도구 `botd`는 6개월 뒤 결국 폐기됨 — 구체적 폐기 사유는 원문에
  명시되지 않음, 워크플로우가 다른 방식으로 진화했을 가능성.
- 정량적 생산성 지표(커밋 수, 배포 빈도, 버그율 등)는 공개되지 않아 "주장(claimed)"
  수준으로만 평가한다.

## 재현 가이드

- **난이도**: 상 (개인 인프라 자동화 도구 `botd`를 직접 구축해야 함)
- **준비물**: VM/컨테이너 프로비저닝 가능한 클라우드 환경, Claude Code·Codex·Cursor
  등 다중 에이전트 CLI, 자격증명 프록시(비밀키를 VM에 직접 저장하지 않는 구조)
- **핵심 단계**:
  1. "에이전트가 완결한다" 원칙을 세우고 사람의 개입 지점을 검토/승인으로 한정
  2. 작업마다 독립 VM을 프로비저닝해 파일·자원 충돌을 원천 차단
  3. 진행상황 추적·히스토리 보존을 자동화(전용 오케스트레이터 또는 기존 도구 활용)
  4. 외부 연동은 읽기전용 우선, 비밀키는 프록시 경유로 격리
  5. 테스트·CI·스크린샷까지 에이전트 루프에 포함해 사람 검토를 결과물 단계로 좁힘

## 강의·AX 활용 포인트

- **강의**: "승인 피로 없이 자율성을 확대하려면 무엇이 필요한가"를 설명할 때, VM 격리가
  Auto Mode류 분류기 기반 승인 완화의 대안적 설계임을 보여주는 사례로 쓸 수 있다.
  [[loop-engineering]]·[[2026-08-07-claude-code-auto-mode-default]]와 나란히 다루면
  "권한 프롬프트 승인 완화" vs "인프라 격리로 승인 자체를 불필요하게 만들기"라는 두 갈래
  설계 철학을 비교할 수 있다.
- **AX**: 정량 성과가 없는 개인 사례이므로 그대로 도입 근거로 쓰기보다는, "다중 에이전트
  병렬 운영 시 격리·권한 설계가 왜 먼저 필요한가"를 논의하는 워크숍 소재로 적합하다.
  같은 날 확인된 Claude Code Auto Mode 우회 사례([[2026-08-07-claude-code-auto-mode-default]])와
  대비하면 "느슨한 분류기 승인" vs "격리 인프라" 두 접근의 리스크 차이를 구체적으로
  설명할 수 있다.
