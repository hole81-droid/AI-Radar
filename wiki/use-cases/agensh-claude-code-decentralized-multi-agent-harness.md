> **공식**: Claude Code로 subagents+hooks를 활용해 오케스트레이터 없는 멀티 에이전트 팀 협업(3~32+ 규모별 3단계 설계)을 구성 → 원 논문 실측 기준 pandoc 재구현 통과율 33.89%→55.06%(1,024 에이전트, 실무 이식 효과는 미실측)

## 무엇을 자동화했나

AX LABS가 Microsoft Research의 논문 "Agensh"(중앙 오케스트레이터 없는 멀티 에이전트 하네스)를
리뷰하고, 그 설계를 **Claude Code 에이전트 팀에 그대로 이식하는 3단계 구현 가이드**로
정리했다. 문제의식은 "에이전트 수를 늘릴수록 중앙 오케스트레이터가 병목이 된다"는 것 —
Agensh는 오케스트레이터 대신 **공유 인프라(Git 기반 워크스페이스·메시징·컨텍스트 보드)**로
워커들이 스스로 작업을 클레임하고 조율하게 한다. 자동화 대상은 "여러 코딩 에이전트를
사람 개입 없이 병렬로 굴리면서도 충돌·중복 작업을 막는 것" 자체다.

## 어떻게 구성했나 (아키텍처)

**공유 인프라 3요소** (Agensh 원 설계):
- **공유 워크스페이스(Git)**: 워커마다 개별 브랜치를 유지해 덮어쓰기를 방지하고 변경 이력·귀속을 보존.
- **메시징(Mattermost 스타일)**: 공개 채널은 낮은 우선순위 업데이트, 다이렉트 메시지는
  새 공유 컨텍스트 항목 같은 긴급 정보 전달용 — 워커가 계속 방해받지 않도록 분리.
- **공유 컨텍스트 보드**: append-only 저장소. 레코드 타입 5종(OBSERVED·FACT·FAIL·CLAIM·
  PATCH_SUMMARY, 각 100자 제한·PATCH_SUMMARY만 300자)으로 워커 간 정보를 짧게 공유.

**5단계 협업 루프**: Gather(목표·동료 진행상황·보드 기록 수집) → Claim(공유 컨텍스트로
하위 작업 선점) → Act(도구 사용+발견사항 게시) → Verify(수락 기준 대조 검증) → Merge(요약과
함께 main에 병합, 충돌 시 해소). 동기화 지점을 강제하지 않아 진짜 병렬 실행이 가능하다.

**Claude Code 이식 — 규모별 3단계 설계** (AX LABS 제안):
1. **3~5 에이전트**: Claude Code 네이티브 에이전트 팀 + `board.py`(파일 잠금 기반 append-only
   보드, `python3 .team/board.py write FAIL "설명" --by 워커명` 형태로 호출)로 공유 컨텍스트
   레이어 추가. 훅 2종: `TeammateIdle`(마감 전 계속 작업하도록 유도, 15분 무응답 시 행동
   촉구 또는 차단), `TaskCompleted`(검증 스크립트 실행, 테스트 실패 시 완료 차단).
2. **8~16 에이전트**: 워커별 컨테이너(리포지토리 클론+공유 Git 업스트림+공유 볼륨 위 보드
   파일). CLAIM 중복 감지로 충돌을 해소하며, 나중에 클레임한 쪽이 양보.
3. **32+ 에이전트**: 완전한 Agensh 스택(Gitea로 PR·이슈 관리, Mattermost로 채널·DM, 보드
   서비스, 워커별 내구성 큐를 갖춘 이벤트 라우터, 분산 워커 인프라 — 예: 16노드×64워커).

**전제조건**: 자동화된 검증기(레퍼런스 바이너리 또는 테스트 스위트)가 있어야 하고, 작업이
병렬 하위작업으로 분해 가능해야 하며, 속도가 중요한 시간 제약이 있고, 토큰 예산은 에이전트
수에 비례해 선형 증가한다는 점을 감안해야 한다.

## 벤치마크 데이터

| 항목 | 값 |
|---|---|
| 모델 | 미확인 (Agensh 원 논문은 특정 LLM 미명시, Claude Code 이식판은 모델 불문 설계) |
| 비용 | 미확인 (에이전트 수에 선형 비례한다는 정성적 언급만 있음) |
| 권한 설계 | 미확인 |
| 성숙도 | prototype (AX LABS가 원 논문을 리뷰하며 제안한 설계 가이드 — 실제 Claude Code 상에서 이 3단계를 운영해 재측정한 결과는 이 글에 없음) |
| 근거 유형 | claimed (수치 자체는 Agensh 원 논문의 ProgramBench 실험 결과이며, Claude Code 이식 후 재현된 실측치가 아니다) |

## 성과와 수치

**원 논문(Agensh, ProgramBench) 실측치** — 바이너리만 보고 프로그램을 재구현하는 벤치마크:
- 단일 에이전트: 5개 과제 평균 19.31%
- 128 에이전트: 28.78%(상대개선 +49%)
- pandoc 단일 과제: 33.89%(1 에이전트) → 55.06%(1,024 에이전트, 상대개선 +62%)
- 속도: 128 에이전트가 pandoc 30% 도달까지 30분, 단일 에이전트는 2시간 이상 소요

**주의**: 이 수치는 Agensh 프레임워크 자체의 실험 결과이지, AX LABS가 Claude Code 위에서
재현해 측정한 수치가 아니다. Claude Code 이식 가이드(3단계 설계·board.py·훅 2종)는
저자의 설계 제안이며, 이 조합으로 실제 운영했을 때의 성과는 이 글에 보고되지 않았다.

## 재현 가이드

- **난이도**: 중 (1단계·3~5 에이전트 기준). 3단계(32+)로 가면 상.
- **준비물**: Claude Code 에이전트 팀 기능, Git 리포지토리, 자동화된 테스트/검증 스위트,
  `board.py` 스크립트(파일 잠금 기반 append-only 로그 — 직접 구현 필요), Claude Code
  hooks(`TeammateIdle`·`TaskCompleted`) 작성 권한.
- **핵심 단계**:
  1. 공유 컨텍스트 보드 스키마를 5개 레코드 타입(OBSERVED/FACT/FAIL/CLAIM/PATCH_SUMMARY)으로
     설계하고 `board.py`로 append-only 쓰기·타입별 조회·AND/OR grep 쿼리를 구현.
  2. 모든 워커에게 **동일한 프롬프트**(워커 ID만 다름)를 부여 — "방향을 묻지 말 것,
     보드의 FAIL을 재시도하지 말 것, 병합 전 검증할 것, 5단계 루프를 무한 반복할 것"을
     명시.
  3. `TeammateIdle` 훅으로 15분 무응답 시 행동을 촉구, `TaskCompleted` 훅으로 검증
     스크립트가 실패하면 완료 처리를 차단.
  4. CLAIM 중복 시 나중에 선점한 워커가 양보하는 규칙으로 충돌을 해소.
  5. 검증기 없이는 전제조건이 성립하지 않으므로, 먼저 자동 채점 가능한 작업인지부터
     확인.

## 강의·AX 활용 포인트

- **강의**: "에이전트를 늘릴수록 오케스트레이터가 병목이 된다"는 멀티 에이전트 설계의
  핵심 트레이드오프를 가르치는 데 좋은 사례 — 중앙집중형(기존 다수 사례의 "오케스트레이터"
  패턴)과 분산형(Agensh) 두 아키텍처를 나란히 비교하는 실습 소재로 쓸 수 있다.
- **AX**: 3단계(3~5 → 8~16 → 32+) 설계는 "지금 우리 조직에 필요한 건 몇 단계인가"를
  판단하는 체크리스트로 쓸 수 있다 — 소규모 팀은 1단계(네이티브 에이전트 팀+보드
  스크립트)만으로 충분할 가능성이 높고, Gitea·Mattermost 급 인프라(3단계)는 실제
  대규모 무인 운영 조직이 아니면 과잉 투자일 수 있다.
- **주의**: 성과 수치가 원 논문 실험치이지 Claude Code 재현치가 아니라는 점을 반드시
  함께 전달할 것 — "이 설계를 그대로 쓰면 pandoc 사례처럼 55%가 나온다"로 오독되지
  않도록 한다.
