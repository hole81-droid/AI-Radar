> **공식**: Claude(+Claude in Chrome)로 공공 연방 조달 데이터 API 조회·크로스필터링·브라우저
> 리드 발굴·자체 메일함 아웃리치를 활용해 건설 하도급 영업 리드 파이프라인을 수행 →
> 필터 통과 12건 중 10건 컨택·8건 회신·3건 계약 성사

## 무엇을 자동화했나

데이터센터 건설 현장에서 하도급으로 일하는 소규모 건설팀 사용자의 사례(글쓴이는 해당
사용자에게 사용 허락을 받아 대신 공유한 이메일 인프라 벤더 Atomic Mail 측 계정).
연방 정부 발주 공사를 수주한 대기업이 하도급업체를 찾을 때, 그 정보가 업계지·입소문으로
퍼질 즈음이면 좋은 하도급 자리는 이미 마감된다는 문제에서 출발했다. 목표는 "누가 방금
연방 건설 계약을 땄는지"를 남들보다 먼저, 자동으로 알아내는 것.

파이프라인은 (1) 공개 연방 지출 데이터에서 신규 수주 건 조회 → (2) 진짜 건설 공사만
걸러내는 교차 필터링 → (3) 수주 기업의 담당자 연락처를 웹에서 탐색 → (4) 에이전트 자체
메일함으로 컨택·회신 관리, 4단계로 구성된다.

## 어떻게 구성했나 (아키텍처)

- **데이터 소스**: USAspending.gov의 JSON API(`spending_by_award`, 계정 불필요, FPDS
  원천)를 Claude가 직접 쿼리하도록 구성 — 결과 구조화까지 약 20분 소요. SAM.gov 공고
  텍스트 API도 병행하되, 공개키는 하루 10회로 요청 제한이 빡빡해 등록 계정(하루 1,000회)
  전환을 권장.
- **핵심 필터링 노하우**: "data center" 키워드만으로 걸러내면 대부분 IT서비스 재판매
  업체(연방정부 용례에서 "data center"는 실제 건물이 아니라 IT서비스를 뜻하는 경우가
  많음)만 걸린다. 여기에 건설·전기공사 표준 NAICS 코드(236220, 238210)를 교차 필터링해야
  실제 시공사만 남는다. 이 과정에서 "VA(보훈부) 전자의무기록 현대화(EHRM) 프로그램이
  데이터센터 개보수 수요를 반복적으로 만들어낸다"는 패턴을 Claude가 여러 수주 건 설명을
  연달아 읽다가 스스로 발견 — 키워드 검색만으로는 못 찾는 인사이트였다는 점이 핵심.
- **날짜 필터의 함정**: API의 날짜 필터는 "거래일" 기준이라, 기존 계약의 단순 수정
  건까지 "신규 수주"처럼 섞여 나온다(활성 계약에 추가 자금이 붙은 것이라 완전히 무가치한
  신호는 아니지만 "방금 수주"와는 다른 의미이므로 재현 시 구분 필요).
- **담당자 탐색 = 브라우저 자동화 구간**: 수주 기록에는 발주처의 계약담당관 정보만 있고
  수주기업의 영업 담당자는 없다. 이 "사람 연결" 부분만 **Claude in Chrome**으로 수주
  기업 웹사이트를 방문해 하도급/공급업체 문의 채널을 탐색 — 구조화 API가 있는 구간은
  API로, 없는 구간(담당자 탐색)만 브라우저 자동화로 처리하는 하이브리드 설계. 초기
  버전은 웹페이지를 직접 스크래핑했다가 레이아웃이 바뀌자 바로 깨졌고, API 기반으로
  바꾼 뒤로는 한 번도 깨지지 않았다는 교훈도 공유됐다.
- **아웃리치**: 에이전트 전용 메일함(Atomic Mail, 처음엔 공유 도메인 → 이후 자사 도메인
  전환)에서 초안 발송·답장 확인을 한 스레드 안에서 자율 처리. 자사 도메인 전환 후
  발신자 주소만으로 회사를 알아본 회신이 늘었다고 언급.
- **작업 상태 관리**: Google Sheets를 리드·연락처·컨택 현황·거래 단계의 단일 소스로 사용.

## 성과와 수치

- 한 조회 구간(윈도우) 기준: 필터 통과 12개 기업 → 10곳 컨택 → 8곳 회신 → 3건 계약 성사,
  2건은 담당자를 못 찾아 미접촉 상태로 남음. 물량이 아니라 "발굴(discovery)"이 병목이었고,
  아웃리치 자체는 상대적으로 쉬웠다는 것이 작성자의 결론(claimed, 자기보고).
- 이메일 인프라 벤더(Atomic Mail) 계정이 고객 사례를 대신 공유하는 형태의 글이라는 점을
  감안해야 한다 — 독립 제3자 검증은 없다.

## 재현 가이드 (난이도: 중~상)

1. USAspending.gov API로 관심 업종의 연방 수주 데이터를 조회하는 쿼리를 Claude에게
   작성시킨다 (계정 불필요).
2. 키워드 하나만으로 필터링하지 말고, 실제 업종을 특정하는 NAICS 코드와 교차 필터링한다.
3. 여러 건의 수주 설명을 한 번에 읽혀 "반복되는 발주 프로그램/패턴"이 있는지 Claude가
   스스로 찾게 한다 — 키워드 검색으로는 안 보이는 반복 수요가 가장 가치 있는 신호.
4. 구조화 API가 없는 구간(담당자 연락처 탐색 등)만 브라우저 자동화(Claude in Chrome)로
   보완한다 — 전 과정을 스크래핑하지 말 것(레이아웃 변경에 취약).
5. 에이전트 전용 이메일 계정을 만들어 발송~답장을 한 스레드에서 처리시키고, 발송 전
   승인 절차를 직접 설계한다(원문에 없는 부분).

## 강의·AX 활용 포인트

- "구조화 데이터가 있는 구간은 API로, 없는 구간만 브라우저 에이전트로" 라는 하이브리드
  설계 원칙은 에이전트 아키텍처 강의에서 재사용도가 높은 교훈이다.
- 공공 조달·입찰 데이터를 활용한 B2B 리드 제너레이션은 건설업 외 다른 업종(의료기기·
  IT 용역 등)에도 동일 패턴으로 일반화 가능 — AX 사례 발굴 시 "공개 정부 데이터 + 에이전트"
  조합의 참고 사례로 제시할 수 있다.
- 다만 이메일 벤더가 자사 고객 사례를 홍보하는 성격의 글이므로, 수치를 인용할 때는
  "자기보고·비검증"이라는 한계를 함께 언급해야 한다.
