> **공식**: xAI의 관리형 에이전트 플랫폼 Grok Bot으로 "Agentic Engineer Bot"(코딩 작업을
> Claude Code·Codex로 라우팅)·"Support Bot"(Freshdesk 티켓 15분마다 모니터링)·개인비서용
> Bot 여러 개를 구성해 5일간 실사용 → 관리형 인프라 덕에 설정은 거의 없었지만 딥 엔지니어링
> 작업의 주력으로 쓰기엔 아직 부족하다는 결론.

## 무엇을 자동화했나

Latent Space 필자가 xAI의 새 에이전트 제품 **Grok Bot**을 5일간 실사용하며 여러
"Bot"(역할별 에이전트)을 구성했다:

- **Agentic Engineer Bot**: 코딩 작업의 성격에 따라 프론트엔드는 Claude Code,
  디버깅은 Codex로 자동 라우팅.
- **Support Bot**: Freshdesk 고객 티켓을 15분 간격으로 브라우저 자동화(browser-agent)로
  모니터링.
- **개인비서 기능**: X 활동 기반 일일 뉴스 브리핑, 여러 계정을 통합한 캘린더 뷰.

## 어떻게 구성했나 (아키텍처)

Grok Bot은 사용자가 서버·API 크리덴셜·MCP 서버를 직접 운용하지 않아도 되는
**"관리형 에이전트 컴퓨터"** — 브라우저 로그인과 플러그인 연결만으로 시작한다.
모델 선택은 자동(내부 라우팅)이며, 사용자는 영어 문장으로 "Bot"의 역할을 정의한다.
저자는 이를 OpenClaw(자체 게이트웨이·설정파일·MCP 서버 운용 필요)와 대비해
**"Grok Bot=새 맥북 언박싱, OpenClaw=리눅스"**로 비유했다.

## 벤치마크 데이터

| 항목 | Grok Bot | OpenClaw(비교 기준) |
|---|---|---|

| 인프라 | 관리형 클라우드 호스팅 | 사용자 소유 게이트웨이(자체 호스팅 또는 선택적 관리형) |
| 모델 선택 | 자동 라우팅(수동 선택 불가) | 수동 모델 선택 가능 |
| 추상화 수준 | 높음(영어 기반 Bot 프로그래밍) | 낮음(코드/인프라 노출) |

## 성과와 수치

- **일화(anecdotal)**: 정량 수치는 공개되지 않았고, 저자 1인의 5일 사용 경험에
  기반한 정성 평가.
- 강점: 행정 업무·요약·프로젝트 관리에서 "훈련이 거의 필요 없는 디지털 비서"로
  유용, 기기 간 연속성 우수.
- 약점: 딥 기술 구현 작업에는 한계, 수동 모델 선택 불가, 컨텍스트 관리가 숨겨져
  있어 투명성이 떨어짐, 하나의 Bot 대화 안에서 작업 경계가 흐려짐.
- 저자 결론: "엔지니어링 그 자체보다는 엔지니어링 주변의 얕은 작업에 꽤 쓸모 있다."

## 재현 가이드

- **난이도**: 하 (관리형 플랫폼이라 진입장벽 낮음, 브라우저 로그인 수준)
- **준비물**: xAI Grok Bot 계정, 연동할 외부 서비스(고객지원 툴·캘린더·X 계정 등)
  플러그인 연결 권한, 라우팅시킬 코딩 에이전트(Claude Code·Codex 등) 접근권
- **핵심 단계**:
  1. 목적별로 역할이 분리된 Bot을 여러 개 정의(엔지니어링 라우터·지원 모니터링·
     개인비서 등)
  2. 코딩처럼 정밀 제어가 필요한 작업은 Bot이 적합한 하위 도구(Claude Code·Codex)로
     위임하도록 설계
  3. 반복적·저위험 모니터링 작업(티켓 확인 등)에 먼저 적용해 신뢰도 확인
  4. 딥 기술 작업은 Bot에 전적으로 맡기지 않고 사람이 주도권을 유지

## 강의·AX 활용 포인트

- **강의**: "관리형·고추상 에이전트 플랫폼"과 "직접 운용하는 오픈 하네스"의
  트레이드오프(설정 부담 vs 통제력)를 대비하는 표준 사례로 쓰기 좋다 — Grok Bot
  vs OpenClaw 비유("맥북 vs 리눅스")는 비개발자 대상 설명에도 바로 쓸 수 있다.
- **AX**: 비개발 부서(고객지원·행정)에는 관리형 에이전트 플랫폼처럼 진입장벽이
  낮은 도구가 먼저 확산될 가능성이 높다는 시사점 — 개발팀에는 통제력이 높은
  도구(Claude Code·Codex류), 비개발 부서에는 관리형 플랫폼이라는 이원화된
  도입 전략을 고려할 근거.
