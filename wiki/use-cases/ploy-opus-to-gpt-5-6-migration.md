# Ploy — 프로덕션 마케팅 웹사이트 빌드 에이전트, Opus 4.8 → GPT-5.6 Sol 마이그레이션

> **공식**: Ploy가 Vercel AI SDK 기반 자체 에이전트로 cli-pipeline 방식을 활용해 프로덕션
> 마케팅 웹사이트 빌드(기획·코딩·이미지 생성·스크린샷·완료 판단)를 수행 → 모델을
> Claude Opus 4.8에서 GPT-5.6 Sol로 교체 후 완료시간 2.2배 단축, 비용 27%↓, 출력토큰
> 약 48%↓ (실측)

## 무엇을 자동화했나

Ploy는 4개월간 프로덕션 평가(eval)에서 최고 성능을 유지해온 Claude Opus 4.8을
GPT-5.6 Sol로 교체했다. 에이전트는 마케팅 웹사이트 빌드 전 과정을 자율 수행한다:
페이지를 기획하고, 코드베이스를 읽고, 컴포넌트를 작성하고, 이미지를 생성하고, 자신의
작업 결과를 스크린샷으로 확인한 뒤 완료 여부를 스스로 판단한다. 이 사례는 벤더 마케팅이
아니라 실제 프로덕션 서비스(ploy.ai)를 운영하는 팀이 직접 마이그레이션하며 겪은 기술적
문제와 실측 벤치마크를 공개한 것이다.

## 어떻게 구성했나 (아키텍처)

- **SDK**: Vercel AI SDK 기반 자체 빌드 에이전트.
- **① 평가 하네스 수정**: 초기 비교에서 실패의 약 1/3이 모델 차이가 아니라 하네스
  설계(순차 실행 전제 예산에 GPT-5.6의 병렬 도구 호출이 초과, 배치 파일 읽기 미지원)
  때문임을 발견하고 하네스를 재정비.
- **② 도구 스키마 재설계**: GPT-5.6이 25개 선택적 파라미터를 전부 `offset: 0` 같은
  임의 기본값으로 채워 넣어(Claude는 미사용 파라미터를 생략) 파일 읽기의 52~64%가
  빈 결과를 반환하는 문제 발생. 선택적 속성을 `anyOf: [T, null]`로 "필수-nullable"화해
  명시적 null을 허용하고 도구 실행 전 이를 제거하는 방식으로 해결 → 빈 파일 읽기
  52%→0%, 도구 호출 수 약 30% 감소.
- **③ 프롬프트 캐시 재구조화**: GPT-5.6이 부분-프리픽스 매칭을 지원하지 않아, 대화·
  전역 단위 캐시 키 대신 워크스페이스 단위 캐시 키가 필요. Anthropic 방식을 본뜬 3계층
  구조(A: 워크스페이스 공용 2.9만 토큰 정적 도구 프리픽스, B: 워크스페이스 컨텍스트,
  C: 세션별 대화 체인)로 재설계 → 첫 호출 캐시 히트율 0%→83.7%, 비캐시 입력 토큰
  28% 감소. 단, 워크스페이스 캐시 키 하나당 처리량이 분당 약 15요청으로 제한되며
  이를 넘으면 별도 콜드 캐시 노드로 트래픽이 분산되는 운영상 트레이드오프 발생.
- **④ 추론 재생(reasoning replay) 방식 변경**: 서버 측 추론 참조 포인터(`rs_...`)를
  찾지 못하는 간헐적 오류가 발생해, `store: false`로 설정하여 암호화된 추론 내용을
  서버 상태 포인터가 아닌 자체 완결적(self-contained) 블롭으로 요청하도록 변경.

## 성과와 수치

- **실측(measured)**: 재설계 평가 스위트(완료된 빌드당 평균)에서 비용 27%↓, 완료시간
  2.2배 단축(54%↓), 입력 토큰 35%↓, 출력 토큰 48%↓, 시각 품질 점수는 오히려 소폭
  상승(+3.4%). GPT-5.6이 동등한 시각 결과를 훨씬 적은 코드로 생성한 사례도 확인됨
  (CSS 2,508자·45개 변수 vs Opus 17,957자·174개 변수).
- **트레이드오프(측정 기반 서술)**: GPT-5.6은 스티어링 없이도 "깔끔하고 격자화된
  레이아웃"으로 수렴하는 경향이 강해, 기존 디자인 시스템을 무시하고 일반적인 결과를
  내는 경우가 있어 브랜드 준수 기준을 맞추기 위한 추가 프롬프트 엔지니어링이 필요했다.
- **커뮤니티 반응(Hacker News, 257점·131댓글)**: 한 코멘터가 여러 워크플로우를 최신
  모델로 옮기며 비용 약 50% 절감을 경험했다고 보고해 부분적으로 교차검증됨. 반면
  Playcode.io 창업자는 "GPT-5.6 Sol이 사실상 5.5 재포장으로 품질 향상이 없다"고
  반박했고, 복잡한 디버깅 작업에서는 Opus 4.8이 더 낫다는 의견도 있었다. 다수 댓글은
  기술 내용보다 블로그 글의 "LLM 특유의 문체"를 지적하는 데 집중됐다.

## 재현 가이드

- **난이도**: 상 (프로덕션 에이전트의 도구 스키마·프롬프트 캐시·평가 하네스를 모델
  전환에 맞춰 재설계해야 하며, 단순 워크플로우 전환("one-liner")과 달리 "진짜 에이전틱
  작업"은 상당한 튜닝이 필요하다고 원문·HN 댓글 모두 강조)
- **준비물**: 프로덕션 평가(eval) 스위트, Vercel AI SDK(또는 동급 에이전트 프레임워크),
  워크스페이스 단위 프롬프트 캐시 설계 역량
- **핵심 단계**:
  1. 모델 전환 전, 실패 원인이 모델 차이인지 하네스(병렬 호출·배치 읽기 지원 여부)
     문제인지 먼저 분리해 진단
  2. 도구 스키마의 선택적 파라미터를 `anyOf: [T, null]` 형태의 필수-nullable로 전환해
     모델별 파라미터 처리 차이로 인한 빈 응답을 제거
  3. 캐시 키 구조를 대화/전역 단위에서 워크스페이스 단위로 재설계하고, 노드당 처리량
     한계(분당 약 15요청)를 감안한 트래픽 분산 설계
  4. 서버 측 추론 상태 참조 대신 자체 완결적 블롭(`store: false`)으로 전환해 추론 재생
     오류를 제거
  5. 시각 품질·비용·시간을 함께 추적하는 평가 스위트로 전후 비교

## 강의·AX 활용 포인트

- 벤더 발표가 아닌 실사용 기업의 실측 마이그레이션 데이터라 신뢰도가 높고, "모델을
  바꾸면 프롬프트만 바꾸면 된다"는 통념을 깨는 좋은 반례 — 강의에서 프로덕션급 모델
  전환의 숨은 비용(스키마·캐시·평가 하네스 재설계)을 설명하는 데 적합.
- AX 관점에서는 특정 벤더 락인 없이 최고 성능 모델을 지속적으로 교체하는 "모델
  애그노스틱" 운영 전략의 실제 사례로 인용 가능. 단, 캐시 처리량 제약(분당 15요청/노드)
  같은 운영상 트레이드오프도 함께 소개해야 균형 잡힌 AX 보고서가 된다.
- HN 스레드의 반박 의견(품질 향상 없음, 복잡한 디버깅에서는 Opus가 우위)도 함께 인용해
  "실측 수치=만능"이 아니라 워크로드별 재현성을 강조하는 균형 잡힌 시각 제공 가능.
