> **공식**: 코딩 에이전트에 second-brain 방식의 구조화된 마크다운 문서 워크플로를 붙여 세션 간 지식 유지를 수행 → RAG 기반 "메모리" 플러그인의 5가지 구조적 결함을 문서화 체계로 대체 (오픈소스 공개, 정량 비교 미실측)

## 무엇을 자동화했나

개발자 Kevin Liao가 Hacker News에서 330점을 받은 글(2026-10-03)에서, 현재 유행하는
AI 에이전트 "메모리" 플러그인들(대화 조각을 임베딩해 벡터DB에 저장했다가 유사도로
불러오는 RAG 방식)이 틀린 전제 위에 서 있다고 주장한다 — 에이전트에게 부족한 것은
"기억력"이 아니라 "제대로 된 문서"라는 것. 이 주장을 바탕으로 벡터DB 없이 순수
마크다운 파일만으로 에이전트의 지속 지식을 관리하는 오픈소스 도구 **Operator Memory**
(github.com/aerovato/operator-memory)를 만들어 공개했다.

## 어떻게 구성했나 (아키텍처)

- **RAG 메모리의 5가지 결함 진단**: ① 유사도로만 호출돼 정확성과 무관하게 표면화됨
  ② 저장된 조각에 주변 맥락이 빠져 있음 ③ 코드베이스가 바뀌면 과거 정보가 그대로
  낡아버림 ④ "모르는 것을 모른다"는 상태라 에이전트가 미지의 정보를 능동적으로
  찾을 수 없음 ⑤ 임베딩 저장소 자체가 감사 불가능한 블랙박스.
- **대안 — 문서 기반 메모리**: 임베딩·요약기·백그라운드 데몬 없이, `internal/` 폴더
  아래에 스펙·계획·리서치 노트·인덱스·결정 기록을 **평문 마크다운**으로 쌓는다.
  전부 읽을 수 있고, git으로 커밋·공유 가능하며, 사람이 직접 감사할 수 있다.
- **작업 루프 재정의**: 기존 "prompt → build → forget"(지시 → 작업 → 휘발) 루프를
  "**prompt → consult → build → update**"(지시 → 문서 열람 → 작업 → 문서 갱신) 루프로
  바꾼다. consult 단계에서 관련 마크다운을 먼저 읽고, update 단계에서 낡은 문서를
  고치거나 새 문서를 만들어 다음 세션에 넘긴다.
- **도구 종속성 없음**: 특정 코딩 에이전트에 묶이지 않은 범용 워크플로로 설계됐다 —
  Claude Code·Codex 등 어떤 에이전트에도 "프로젝트 루트에 폴더를 만들고 그 안을
  읽고 쓰게 한다"는 원칙만으로 적용 가능하다.

## 성과와 수치

- 정량적 전후 비교(예: 벡터 메모리 대비 정확도·속도)는 제시되지 않았다 — 글은
  RAG 메모리의 구조적 결함에 대한 **논증**과 대안 워크플로 제안이 핵심이고,
  "효과가 몇 % 개선됐다"는 식의 실측치는 없다.
- 화제성 신호: Hacker News 330점(2026-10-03 기준, `search_by_date` 확인)으로
  같은 날 전체 글 중 상위권에 들었다.

## 재현 가이드

- **난이도**: 하. 별도 인프라(벡터DB·임베딩 API) 없이 프로젝트 루트에 폴더 하나와
  에이전트에게 "작업 전 이 폴더를 읽고, 작업 후 갱신하라"는 지시(CLAUDE.md/AGENTS.md
  등 프로젝트 지시문에 넣을 수 있음)만 있으면 시작할 수 있다.
- **준비물**: 코딩 에이전트(Claude Code·Codex 등), git 저장소, 문서 폴더 구조에 대한
  팀 합의(스펙/계획/리서치/인덱스/결정기록 등 카테고리 구분).
- **핵심 단계**:
  1. 프로젝트 루트에 `internal/`(또는 팀이 정한 이름) 폴더 생성.
  2. 프로젝트 지시문 파일에 "작업 시작 전 관련 문서를 먼저 읽고(consult), 끝나면
     문서를 갱신(update)하라"는 규칙 추가.
  3. 스펙·결정기록·인덱스 등 문서 유형별 템플릿을 미리 정의.
  4. Operator Memory(오픈소스) 또는 자체 구현으로 "읽기→갱신" 루프를 강제.
  5. 문서가 오래돼 낡는지 주기적으로 사람이 감사(RAG의 "조용히 낡는" 문제를
     문서 기반 방식도 완전히 막지는 못하므로).

## 강의·AX 활용 포인트

- **강의**: "에이전트 메모리"를 가르칠 때 벡터DB·임베딩 중심 설명 일변도에서 벗어나,
  "마크다운 문서 자체가 메모리가 될 수 있다"는 대안 관점을 추가 사례로 쓸 수 있다.
  이 저장소(AI Radar) 자체가 `wiki/`를 마크다운으로만 유지하는 동일한 패턴이라
  "왜 이 위키가 벡터DB 없이 운영되는가"를 설명하는 교보재로도 바로 쓸 수 있다.
- **AX**: 사내 에이전트 도입 시 "메모리 플러그인부터 도입"하는 대신, 먼저 "문서화
  체계가 감사 가능한가"를 점검하라는 체크리스트로 활용 가능. 다만 이 글 자체는
  정량 비교 실험이 없는 **한 개발자의 설계 논증**이므로, 도입 전 자체 환경에서의
  검증이 필요하다는 점을 함께 전달해야 한다.
